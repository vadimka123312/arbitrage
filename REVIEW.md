## Кратко

Esports Arb Scanner — локальный сканер арбитражных вилок на победителя киберспортивного матча между Polymarket, Kalshi, Stake и BC.Game (Python 3.11+, FastAPI, SQLite, дашборд на чистом JS). Ставки он не размещает, только показывает возможности.

**Вердикт.** Инженерное качество кода выше среднего: математика вилок корректна, тесты сильные, безопасность по умолчанию продумана. **Для решений с реальными деньгами проект пока не готов:** устаревшие котировки могут считаться свежими, матчер иногда склеивает разные команды, риски правил расчёта и лайва только показываются, статистика прибыли завышена. Это совпадает с собственным вердиктом проекта NOT READY (`docs/handoff/STATUS.md:72`). Отдельная организационная проблема — в репозитории лежит только zip-архив.

## Высокая важность

### В-1. В репозитории только zip-архив

**Где:** единственный файл репозитория — `arbitrage1.zip`, один коммит «Add files via upload» в `main`. [Проверено]

- GitHub не видит исходников: нет диффов, blame, построчного ревью и поиска по коду.
- `.github/workflows/ci.yml` лежит внутри архива, поэтому CI ни разу не запускался: у репозитория 0 workflow и 0 запусков.
- В архиве лежит рабочая база `arb_copy.db` (1,2 МБ: 796 вилок, 2 801 запись аптайма), хотя `.gitignore:20` исключает `*.db`. Секретов в ней нет, но рабочим данным в репозитории не место.
- Репозиторий публичный и без лицензии.
- Процесс противоречит правилу самого проекта «одна задача = одна ветка = один PR; в main напрямую не пушить» (`CLAUDE.md:10`).
- `README.md:47` предлагает клонировать `lndrosa/arbitrage`, который `docs/handoff/STATUS.md:150-151` называет приватным. Хеши коммитов и статусы PR и CI из handoff-документов в этом репозитории проверить нельзя.

**Последствия:** изменения невозможно ревьюить, CI не защищает `main`, каждое обновление — новый бинарный blob.

**Что сделать:** распаковать дерево в корень репозитория; удалить из git zip и `arb_copy.db` (тестам — небольшую синтетическую базу старой схемы); добавить LICENSE; исправить URL в README; включить защиту ветки `main` с обязательным CI.

### В-2. Свежесть котировки не отражает возраст данных

Движок отбрасывает котировки старше `stale_seconds` (10 с), но «время обновления» у площадок означает разное:

| Площадка | Что считается временем обновления | Где |
|---|---|---|
| Polymarket, WebSocket (режим по умолчанию) | каждый PONG помечает все готовые стаканы как обновлённые сейчас | `backend/adapters/polymarket.py:472-489` |
| Kalshi, WebSocket (при заданных ключах API) | каждый успешный ping обновляет `book_ts` всех стаканов без новых данных; стаканы WebSocket через REST не сверяются | `backend/adapters/kalshi.py:550-569`, `:438` |
| Kalshi, top-of-book из `/events` | текущее время, без времени источника | `backend/adapters/kalshi.py:104-114`, `:314-320` |
| BC.Game | время нашего успешного опроса; `generated` источника отклоняется, только если оно «из будущего» | `backend/adapters/bcgame.py:249-263`, `:495` |
| Stake | время запроса; `updatedAt` провайдера игнорируется | `backend/adapters/stake.py:419` |

**Доказательства [Проверено]:**
- Kalshi: стакан возрастом 600 с (`is_fresh=False`) после одного успешного ping без единого кадра данных получает возраст 0,5 с и `is_fresh=True`.
- BC.Game: при `generated` 600 с назад возраст котировки в модели — 0,0 с, `is_fresh(10)=True`. Если источник «замёрз», через 30 мин данным 1 800 с, а для модели им 0 с.

**Последствия:** живое соединение с мёртвым или отписанным каналом либо замёрзший источник дают старые цены с пометкой «свежие» — классический источник фантомных вилок. У Polymarket окно ограничено REST-ресинком раз в 30 с (если его не отвергает защита по времени, см. С-3). У Kalshi в режиме WebSocket сверки нет, и устаревший стакан может считаться свежим бесконечно. По собственному 30-минутному наблюдению проекта порог свежести 10 с прошли лишь 0,689 % из 45 312 замеров (`docs/handoff/NEXT_STEPS.md:24`).

**Что сделать:**
- разделить «канал жив» и «данные свежие», обновлять время только по кадрам с данными;
- учитывать время источника (`sending_ts_ms`, `generated`, `updatedAt`) и ограничивать его возраст;
- раз в 30–60 с сверять стаканы WebSocket через REST;
- выключить BC.Game по умолчанию, пока свежесть не подтверждена.

### В-3. Матчер автоматически склеивает похожие, но разные команды

**Где:** `backend/matching/matcher.py:82-88,114-118`, `backend/matching/normalizer.py:21-29,159-164`, пороги — `backend/config.yaml:165-179`.

Уверенность считается как 0,7 × сходство команд + 0,2 × время + 0,1 × формат. Если обе площадки публикуют формат (BO3) и время совпадает, для авто-сопоставления (порог 85) хватает сходства названий 78,6 из 100, а лишнее слово в названии стоит всего 15 баллов.

**Доказательства [Проверено]:**

| Одна площадка | Другая площадка | Результат |
|---|---|---|
| G2 Esports vs Vitality, BO3 | G2 Ares vs Vitality, BO3 | авто, 89,5 |
| Team Liquid vs NIP | Team Liquid Brazil vs NIP | авто, 89,5 |
| Cloud9 vs Evil Geniuses | Cloud9 Blue vs Evil Geniuses | авто, 89,5 |
| Hanwha Life Esports vs T1 | Hanwha Life Esports Challengers vs T1 Challengers | авто, 89,5 |
| Eternal Fire | Eternal Flame | авто, 86,0 |

- В сквозном прогоне с подобранными ценами движок показал для пары G2 вилку «Vitality на Polymarket + G2 Ares на Stake, 22,58 %».
- Тест `tests/test_normalizer.py:74-75` фиксирует сходство «G2 Ares» и «G2» = 85 с комментарием «needs review», но при известном формате это даёт уверенность 89,5, то есть авто-сопоставление.
- Тест `test_partial_name_goes_to_review` (`tests/test_matcher.py:68-71`) проходит только потому, что хелпер `ks()` (`tests/test_matcher.py:23-24`) всегда задаёт `best_of=None`. С `best_of=3` тот же сценарий даёт авто-сопоставление с уверенностью 89,5.
- Под риском в первую очередь пары Polymarket и Stake: формат публикуют они, а Kalshi и BC.Game — нет. Поле турнира матчер не использует, в списке квалификаторов нет «Challengers», цветов и региональных меток.
- Ориентация команд (`swapped`) выбирается нечётко (`matcher.py:82-88`), а вручную подтверждённые пары сохраняются без нижнего порога (`matcher.py:155-166`). Для подтверждённой пары Vitality/TYLOO против Vitality/Tianba ориентация получается `swapped=True`, и обе ноги вилки оказываются на одной команде.

**Последствия:** неверное сопоставление превращается в фейковую вилку и прямой убыток.

**Что сделать:**
- отдельный жёсткий порог для авто: сходство каждой команды не ниже ~95, лишнее значимое слово — только на ручную проверку;
- сравнивать турнир, если он известен с обеих сторон;
- расширить список квалификаторов;
- определять ориентацию по каждой команде с порогом и не принимать слабые ручные пары;
- тесты с известным форматом на обеих сторонах.

### В-4. Разные правила расчёта только показываются, парсер правил «открыт на отказ»

**Где:** `backend/matching/rules.py:92-113,171-201`, `backend/engine/scanner.py:226-257`. Подтверждение вилки зависит только от времени (`backend/engine/tracker.py:63-65`).

- Расхождения правил (отмена, перенос, форфейт, ничья) — лишь предупреждения: на подтверждение и статистику они не влияют.
- «Неизвестные» правила получают самый низкий уровень риска. У BC.Game профиль правил пустой, поэтому все шесть расхождений с Polymarket получают уровень INFO. [Проверено]
- Парсер не распознаёт «settled at 0.50», «last traded price», «50 percent». Фраза «If the match is cancelled, all bets are void. A tie resolves 50-50.» разбирается как «отмена → 50/50», а отрицание «will not resolve to 50-50» — тоже как 50/50. [Проверено]
- Данные: предупреждения о правилах есть у всех 796 записей истории, у 712 из них — о выплате 50/50 на Polymarket. [Проверено]

**Пример убытка:** Polymarket 0,55 + Stake 0,40 (коэффициент 2,5) показываются как +5,3 %. При отмене матча Polymarket платит 0,50 за контракт, а Stake возвращает ставку: итог около −5,3 %.

**Что сделать:** считать неподтверждённые правила как минимум средним риском; не подтверждать вилки с высоким риском или явно исключать их из итогов; разбирать отрицания по предложениям.

### В-5. Большинство вилок найдено после начала матча, задержки лайва не учитываются

**Данные [Проверено, `arb_copy.db`]:**

| Пара площадок | Всего записей | После планового начала |
|---|---:|---:|
| Kalshi + Polymarket | 544 | 477 (88 %) |
| Polymarket + Stake | 168 | 14 (8 %) |
| Kalshi + Stake | 84 | 1 (1 %) |
| **Итого** | **796** | **492 (62 %)** |

- Даже среди подтверждённых вилок 154 из 374 (41 %) найдены после начала матча.
- Из 12 самых прибыльных записей (10,5–33,8 %) 10 найдены после начала матча, 7 прожили меньше 3 с, подтверждены только 4.
- Пример: Leon Esports 0,85 на Polymarket + Tenacity 0,01 на Kalshi дали «15,3 %» примерно через 78 мин после начала; вилка прожила 1,5 с. Похоже, одна из площадок просто запоздала с ценой во время игры.

**Код:**
- Polymarket публикует задержку исполнения для лайв-рынков (`secondsDelay`) и флаг `clearBookOnStart`. Адаптер сохраняет их, но нигде не использует (`backend/adapters/polymarket.py:274-275`). [По коду]
- Лайв-рынки остаются в работе 8 часов после старта (`backend/config.yaml:162`); в таблице такие вилки лишь помечаются как лайв (`backend/engine/arb.py:398`).
- Режим «только pre-match» у Stake опирается лишь на статус провайдера (`backend/adapters/stake.py:246-263,417`): через 10 мин после планового начала при статусе `active` рынок открыт и не помечен как лайв. [Проверено] BC.Game такие матчи отсекает по часам (`backend/adapters/bcgame.py:441`).

**Вывод (интерпретация):** вилки во время игры, живущие 1–3 с, почти наверняка неисполнимы — цены меняются быстрее, чем доходят данные и исполняются ордера.

**Что сделать:**
- настройка `include_live` для каждой площадки, по умолчанию выключенная;
- для лайва на Polymarket требовать возраст данных больше `secondsDelay` или исключать такие рынки;
- фильтр по часам для Stake с допуском на поздний старт;
- в статистике разделять pre-match и лайв.

### В-6. «5 секунд непрерывно» не проверяет непрерывность, а цикл событий блокируется

**Где:** `backend/engine/tracker.py:63-65,72-89`.

- Подтверждение — это `now − first_seen ≥ 5 с`; наблюдения между этими моментами не проверяются.
- Обратная сторона: один пропущенный тик закрывает вилку и перезапускает таймер — гистерезиса нет.

**Доказательства [Проверено]:**
- Наблюдения в 0 с и 6 с — вилка подтверждена (пример в приложении).
- После блокировки цикла на 5,8 с вилка, последний раз виденная на 1,4 с, подтвердилась на 7,2 с без единой оценки в промежутке.
- В истории 796 записей приходятся на 193 вилки; 89 подтверждённых записей начались не позже чем через 10 с после закрытия предыдущего появления той же вилки.

**Что блокирует цикл событий:**
- BC.Game: каждый опрос синхронно копирует (`deepcopy`) и сравнивает всё состояние по всем видам спорта (`backend/adapters/bcgame.py:327-338`), хотя киберспорт — 49 из 2 098 событий, около 2 % (`docs/API_NOTES.md:181`). По замеру самого проекта слияние занимает в медиане 478 мс, p95 — 548 мс (`docs/BCGAME_FRESHNESS.md:48`), и так на каждом цикле опроса. На синтетических данных в песочнице оно занимало от 0,9 с (300 событий) до 10 с (2 500 событий); прототип copy-on-write дал тот же результат за 0,84 мс вместо 3 155 мс. [Проверено]
- Запись истории ждёт общую блокировку БД (`backend/engine/scanner.py:347-353`, `backend/storage/db.py:260-264`); CSV-экспорт 100 тыс. строк держит её 7,3 с — см. С-9.
- Синхронный перематчинг — см. С-10.

**Что сделать:** считать разрывом `now − last_seen` больше ~3 тиков; вместо мгновенного закрытия дать допуск 1–2 с на пропуски; у BC.Game отфильтровывать лишние виды спорта до слияния и использовать copy-on-write; логировать медленные тики.

### В-7. Статистика прибыли завышена

**Где:** `backend/honest_stats.py:240-259,286-348,356-363`, пороги — `backend/config.yaml:185-186`.

**Доказательства [Проверено на `arb_copy.db`]:**
- Повторные появления одной вилки считаются независимыми, полностью профинансированными сделками. При лимите $100 на вилку и банке от $5 000 итог — $256,37, а если учитывать каждую вилку один раз — $109,66, в 2,3 раза меньше. При банке $1 000 эффект скрыт нехваткой капитала ($74,43).
- Итог сильно зависит от срока расчёта: `settle_hours` 0, 3 и 12 дают $134, $74 и $39. Три часа для BO3 и BO5 с учётом выплаты — вероятно, оптимистично.
- Итог формируют выбросы и мелочь: медианная прибыль подтверждённой вилки — $0,21, у 64 % она меньше $0,50, у 77 % — меньше $1. Одна запись даёт 50,8 % суммы $1 250,72, первая десятка — 76,1 %. Фиксированное «без топ-10» обнуляет итог в окнах, где вилок 10 или меньше.
- Пороги по умолчанию `min_profit_pct: 0` и `min_volume_usd: 0`: проходит вилка 0,012 % с прибылью $0,01.
- 53 % обнаружений (422 из 796) не дожили до подтверждения и не входят в статистику времени жизни.
- Не моделируются: задержка и проскальзывание после подтверждения, риск одной ноги, разные правила расчёта (В-4), раздельные балансы на площадках, задержки лайва (В-5). Результаты paper-проверок на прибыль не влияют.

UI и CLI честно называют сумму «верхней оценкой», но цифры всё равно создают ложное впечатление о доходности.

**Что сделать:**
- ограничить суммарную ставку на вилку или матч до расчёта;
- `settle_hours` не меньше 6 и показ чувствительности к нему;
- процентное отсечение выбросов вместо «топ-10»;
- ненулевые пороги по умолчанию, например от 0,5 % и от $10;
- дисконт по выживаемости из paper-проверок;
- раздельная статистика pre-match и лайв.

## Средняя важность

### С-1. Уровни стакана не валидируются

`backend/models.py:16-21`: цена и объём — обычные float без ограничений.
- Цена 0 даёт вилку «100 %», цена −0,2 — «233 %». [Проверено, пример в приложении]
- NaN-объём в режиме `walk_book` вызывает бесконечный цикл в `backend/engine/arb.py:231-250`: `min(nan, x)` возвращает nan, и индексы уровней не сдвигаются. [Проверено: процесс пришлось убить через 8 с] Обработчик ошибок на уровне пары зависание не ловит — встаёт весь цикл событий. В режиме `best_level` NaN-объём даёт `IndexError` (`backend/engine/arb.py:325`).
- Kalshi `parse_book` пропускает цены вне (0; 1) и NaN-цены, проверяя только объём; `to_float` принимает "nan" и "inf" (`backend/adapters/kalshi.py:80-96`, `backend/adapters/common.py:58`).

Сейчас парсеры отбрасывают NaN-объёмы, так что это защита в глубину, но с катастрофическим сценарием отказа.

**Что сделать:** ограничения в `Level` (0 < price < 1, size > 0, без NaN и inf); отбрасывать плохие уровни в `set_books`; отбраковывать «перекрещенный» стакан; параметризованные тесты.

### С-2. Polymarket переподключается без нарастающей паузы

`backend/adapters/polymarket.py:432-433`: пауза сбрасывается после первого снапшота. Заглушка «принять соединение → отправить стакан → закрыть» дала 16 подключений за 12 с. [Проверено] У Kalshi такая защита есть (`WS_STABLE_SECONDS`, `backend/adapters/kalshi.py:117,533`). Риск — шторм переподключений и бан.

**Что сделать:** применить то же правило «стабильного аптайма».

### С-3. Polymarket применяет дельты стакана без проверки порядка

`backend/adapters/polymarket.py:63-75,518`:
- `snapshot()` отклоняет устаревшие данные, а `apply()` — нет: дельта с ts=900 перезаписала уровень стакана с ts=1000. [Проверено]
- Одна дельта с неверным масштабом времени «закрепляет» `book.ts`: свежие снапшоты и REST-ресинк потом отбрасываются как «старые», а PONG держит стакан «свежим» (в REST 0,90, в стакане осталось 0,55). [Проверено, требует ошибочного времени от сервера]
- Отклонённый снапшот всё равно помечает токен готовым; поле `hash` не проверяется.

**Что сделать:** отбрасывать дельты с ts < `book.ts` и ts > now + Δ; не засчитывать отклонённый снапшот; сверять `hash`.

### С-4. REST-запросы стаканов работают по принципу «всё или ничего»

`backend/adapters/kalshi.py:460-462`, `backend/adapters/polymarket.py:587-589`: если в пакете из 100 тикеров не хватает одного, не сохраняется ни один из 99 хороших стаканов; ошибка 503 во втором пакете отменяет первый. [Проверено] У Kalshi без ключей (режим по умолчанию) REST — единственный источник цен, так что пакет «гаснет» до следующего discovery, то есть на срок до 60 с.

**Что сделать:** сохранять результат по пакету или тикеру, помечать устаревшими только отсутствующие.

### С-5. Один битый `startTime` в Stake роняет discovery всех игр

`backend/adapters/stake.py:50-55`: `ms_to_dt` ничем не защищена. `startTime=1e20` даёт `OSError [Errno 75]`, `1792173600000000` — `ValueError: year 58761 is out of range`. [Проверено] Исключение не сетевое, поэтому `fetch_markets()` падает целиком. BC.Game защищён на уровне отдельного события (`backend/adapters/bcgame.py:431-434`).

**Что сделать:** возвращать `None` или ловить ошибку на уровне фикстуры.

### С-6. Хрупкие места адаптера BC.Game

- Изменение косметического поля соперника (например, `logo`) удаляет рынок победителя до следующего движения цены, потому что сравнивается весь словарь (`backend/adapters/bcgame.py:86-92`). [Проверено] Сравнивать нужно пары (id, name).
- Расхождение часов не оценивается, есть только статичная проверка ±5 с (`backend/adapters/bcgame.py:252-263`, `backend/config.yaml:146`). Если часы источника на 6 с впереди, каждый опрос падает с «source timestamp is in the future» без подсказки проверить часы. [Проверено] Для домашних ПК на Windows сценарий реальный.
- После 401, 403 или CloudFront-503 адаптер «защёлкивается» до перезапуска, повторной проверки нет. [По коду]
- После ответов 400, 404 или 410 на курсор 5 из 5 опросов повторяют тот же курсор. [Проверено, заглушка]

**Что сделать:** оценивать и ограничивать смещение часов; после N ошибок брать свежий снапшот; повторно проверять доступ раз в 10–15 мин.

### С-7. Проверка здоровья не видит падения цикла расчёта

`backend/engine/scanner.py:89-92` запускает фоновые задачи без супервизора; `/api/health` (`backend/api/server.py:120-123`) и запись аптайма не учитывают `last_eval_at`.
- Задача оценки отменена, а `/api/health` отвечает `ok`, все площадки «healthy», аптайм пишется как здоровый. [Проверено]
- Дашборд это ловит (`frontend/js/store.js:63-108`), а скрипты и «честная» статистика — нет.
- Аптайм — это `all(...)` по площадкам (`backend/engine/scanner.py:180-183`): одна заблокированная по региону площадка обнуляет аптайм всего сканера. [По коду]

**Что сделать:** супервизор задач с done-callback; учитывать задержку оценки в health и аптайме; считать аптайм по площадкам.

### С-8. Небезопасные режимы запуска и изменение настроек без авторизации

**Где:** `backend/api/server.py:43,261-263`, `backend/run.py:56-61`, `.env.example:6-7`.
- `ARB_ALLOWED_HOSTS='*'` выключает сразу обе проверки, Host и Origin: `Host: evil.com` получает 200, кросс-доменный `PUT /api/settings` — 200, WebSocket с `Origin: http://evil.com` — 101. Предупреждения при старте нет. [Проверено]
- С `--host 0.0.0.0` компьютер в локальной сети с заголовком `Host: localhost` получает 200 на чтение состояния, изменение настроек и подтверждение пар. [Проверено] В логе при этом написано «only these host names are answered».
- Изменение настроек без авторизации принимает `confirm_seconds=0`, `stale_seconds=600`, `min_profit_pct=-100` и сохраняет их в SQLite. При каждом старте эти значения молча перекрывают `config.yaml` (`backend/engine/scanner.py:81-86`).
- Нет CSP, X-Frame-Options, nosniff и Referrer-Policy (`backend/api/server.py:107-115`). Дашборд можно встроить во фрейм и подсунуть пользователю клик по кнопкам подтверждения или блокировки (clickjacking).
- Origin сверяется только по имени хоста, без порта, поэтому страница на `http://localhost:9999` может писать в API. [Проверено]
- `/docs` загружает Swagger с CDN.

В режиме по умолчанию (127.0.0.1) всё закрыто корректно — см. «Сильные стороны».

**Что сделать:** токен на запуск для режимов вне loopback; громкое предупреждение или отказ при `*`; сверять Origin вместе с портом; добавить заголовки безопасности. Фронтенд к CSP уже готов: один модульный скрипт, нет inline-обработчиков.

### С-9. Одна блокировка БД связывает экспорт и запись истории с циклом расчёта

`backend/engine/scanner.py:347-353`, `backend/storage/db.py:260-264`: одно соединение и один `asyncio.Lock` на все операции.
- CSV-экспорт 100 тыс. строк держит блокировку 7,3 с. На синтетической годовой базе (146 тыс. строк) экспорт шёл 14,9 с, и запись сканера всё это время ждала. Экспорт молча обрезается до 100 тыс. строк. [Проверено]
- Неудачная запись истории только логируется — уже снятые с учёта закрытые вилки теряются. [По коду]
- После ошибки `executemany` транзакция остаётся открытой, и частичный пакет фиксируется следующим, не связанным коммитом (1 строка из 3). Отменённый вызов отпускает блокировку, пока поток БД ещё работает. [Проверено]

**Что сделать:** отдельное read-only соединение и потоковая выдача для экспорта и истории (для статистики так уже сделано); очередь записи с повтором; rollback при ошибке.

### С-10. Синхронный перематчинг O(n·m) в цикле событий

### С-11. Во фронтенде сбои выглядят как нормальная работа

## Сильные стороны

**Математика и комиссии**
- `backend/engine/arb.py:28-58`: `Execution` — единый источник стоимости, прибыли и процента. Фильтры, таблица пар, сортировка трекера и capture используют одни и те же значения за вычетом комиссий. В `arb.py` и `fees.py` используются только ask-цены: bid, mid и last там не встречаются.
- 6 997 случайных исполнений `best_level` и `walk_book` сверены с независимой моделью на `Decimal`. В обеих ногах равное число контрактов, ни один уровень не перерасходован, минимумы соблюдены, прибыль совпадает с точностью до 5e-5.
- Ручные расчёты тоже сходятся: Stake 2,60 с лимитом $50 против Kalshi 0,55 даёт затраты $123,76 и прибыль $6,24 (5,042 %).
- `backend/engine/fees.py:18-22`: безопасное округление до цента, агрегация по ордеру, множители серий. Тесты комиссий привязаны к опубликованным таблицам (`tests/test_fees.py:17-23`).
- `backend/adapters/stake.py:122-135`: точная конверсия коэффициента в цену; NaN, inf и коэффициенты ≤ 1 отбрасываются.

**Адаптеры**
- Стаканы сортируются явно (`backend/adapters/kalshi.py:94`, `backend/adapters/polymarket.py:78-81`); ask-цены и объёмы Kalshi правильно выводятся из противоположных bid.
- Подпись Kalshi WebSocket (RSA-PSS, SHA-256) соответствует документации, секреты в логи не попадают (`backend/adapters/kalshi.py:484-505`).
- BC.Game и Stake работают только через GET, без cookies и Authorization; это закреплено тестом `tests/test_bcgame.py:136-147`.
- Прокси не раскрывает учётные данные: `trust_env=False`, ошибки очищаются (`backend/adapters/bcgame.py:141-146`).
- Рынки отбираются строго (`backend/adapters/bcgame.py:441-469`), состояние фида обновляется атомарно.
- Discovery закрывается на отказ: обрезанная пагинация и битые страницы не публикуют полуданные, события с тремя исходами пропускаются.

**Движок**
- Сбой одной пары, capture, paper-проверки или записи в БД не останавливает тик; `CancelledError` пробрасывается.
- Память ограничена: за смоделированные ~50 минут работы с ротацией рынков RSS вырос с 73 до 75 МБ. [Проверено]
- Paper-проверки переиспользуют `evaluate_pair` и дедуплицируются по `(arb_id, first_seen)` (`backend/engine/paper.py:131-133`), очередь и параллелизм ограничены. Пути к размещению ордеров нет.
- Горячий путь быстрый: около 11 мс на тик для 212 пар.

**API, БД, статистика**
- Безопасные умолчания: `Host: evil.com` получает 400 и по HTTP, и при рукопожатии WebSocket; чужой или `null` Origin — 403; CORS preflight — 405; 9 вариантов обхода путей — 404. [Проверено]
- Весь SQL параметризован, история листается по ключу (`backend/storage/db.py:336-339`), CSV нейтрализует формулы `= + - @` (`backend/storage/db.py:189-194`), YAML грузится через `safe_load`.
- SQLite работает вне цикла событий (`to_thread`, WAL), для статистики — отдельное read-only соединение.
- Миграции аддитивны и идемпотентны: на базе автора 796 строк остались нетронутыми, `integrity_check` — ok. [Проверено]
- Границы дня корректно учитывают переход на летнее время (проверено на 23- и 25-часовых днях); банкролл-симуляция блокирует капитал до расчёта; суммы честно подписаны как верхняя оценка.

**Фронтенд**
- Экранирование: `esc()` обрабатывает кавычки; ссылки проходят через `safeUrl` с `rel="noopener noreferrer"`, цвета — через белый список, тосты — через `textContent`; нет `eval` и inline-обработчиков.

**В-3. Авто-сопоставление «G2 Esports» и «G2 Ares»**

```python
from backend.config import load_settings
from backend.matching.matcher import Matcher
from backend.matching.normalizer import TeamNormalizer
from tests.conftest import T0, make_market

s = load_settings()
cfg = s.matching
norm = TeamNormalizer.from_file(s.resolve_path(cfg.aliases_file),
                                subset_penalty_per_token=cfg.subset_penalty_per_token,
                                qualifier_mismatch_cap=cfg.qualifier_mismatch_cap)


def market(platform, market_id, team_a, team_b):
    return make_market(platform, market_id, team_a, team_b, asks_a=[(0.5, 10)], asks_b=[(0.5, 10)],
                       start=T0, best_of=3, game="cs2")


result = Matcher(cfg, norm).match([market("polymarket", "1", "G2 Esports", "Vitality")],
                                  [market("stake", "2", "G2 Ares", "Vitality")])
print(len(result.pairs), result.pairs[0].confidence)  # 1 89.5: авто-сопоставление при пороге 85
```
